01 — Overview

From two isolated signals to a single critical alert

This project reproduces the logic of a detection funnel: the Edge sensor spots reconnaissance (scans), and the Internal sensor confirms exploitation (brute force). Splunk correlates the two on the same source IP within a 60-second window and triggers a critical alert notified by email — nothing here is theoretical; every command and screenshot in this report comes from a real run.

03 — Phase 2

Simulated attack — nmap then Hydra over loopback

With no separate target machine available on the VM's network, the tests were ultimately run over loopback, via a dedicated Suricata sensor listening on the lo interface.

(nmap -sS -p22,8000,8080 -T4 --max-retries 2 127.0.0.1 && \
hydra -l kali -P /usr/share/wordlists/rockyou.txt ssh://127.0.0.1 -t 4 -f)
Wrong target — the initial scan targeted IP 192.168.124.128, which turned out to be the Kali VM itself rather than a separate target: the traffic went through the loopback interface, which the sensors on eth0 never monitored. Fixed by adding a dedicated sensor on the lo interface.
No rules loaded — rules_loaded=0 on both sensors: neither suricata-edge nor suricata-internal had ever run suricata-update. Fixed by running the ruleset update (Emerging Threats Open, ~69,171 rules) in each container.
AF_PACKET conflict — cluster-id 99 already in use when both sensors on eth0 were restarted simultaneously. Fixed by restarting the containers sequentially rather than in parallel.
04 — Phase 3

Correlation in Splunk Enterprise

The SPL query classifies each Suricata alert into one of two phases (edge / internal, based on the signature), then computes the time gap between the last Edge alert and the Internal alert that follows it.

index=main source="*/localtest/eve.json" event_type="alert"
| eval sig=mvindex('alert.signature',0)
| eval phase=if(match(sig,"SSH"),"internal","edge")
| sort _time
| eval edge_ts=if(phase="edge",_time,null())
| streamstats current=t last(edge_ts) as last_edge_time
| where phase="internal"
| eval delta_time = _time - last_edge_time
| where delta_time >= 0 AND delta_time <= 60
| stats earliest(_time) as first_alert, min(delta_time) as min_delta,
        values(sig) as internal_signatures, dc(sig) as nb_alerts by src_ip, dest_ip
| eval status="CRITICAL: Funnel Attack Detected"
| table status, src_ip, dest_ip, min_delta, nb_alerts, internal_signatures
Wrong index — the inputs.conf stanzas specified index=suricata, which did not exist in Splunk: the data was actually indexed in main. Fixed by adapting all the queries.

Scheduled alert and email notification

06 — Troubleshooting

What actually broke (and how it was fixed)

In the interest of honest documentation, here are the real incidents encountered along the way — these are the moments that build real operational skill, not the steps that worked on the first try.

eve.json file frozen after truncation. An attempt to reset the Splunk checkpoint (btprobe) followed by truncating the file left the monitoring stuck on an old event total. Fixed by cleanly recreating the input on a fresh file.
Invalid cron expression. The field contained ***** instead of * * * * * — the Splunk form did not accept spaces typed directly. Fixed by pasting the expression rather than typing it character by character.
Incomplete JSON extraction. The event_type field was sometimes not natively extracted depending on the source, requiring spath or a check via props.conf (KV_MODE=json) to make parsing reliable.
Credential hygiene. The SMTP password was reconfigured after several attempts with the wrong type of credential — a reminder that secrets should be dedicated credentials (app password), never the account's main password.
